# F9: durable email retry and worker health

Local patch only. No production secret, extension, job, data, migration, or
deployment was changed. Baseline: `d893e3551149de05cb24311ed50c7d70134aec1e`.

## Contract

The dispatcher previously converted claim errors, exceptions, and non-array
responses to zero counters. The POST worker returned HTTP 200 for these failures.
It now validates the entire claimed batch before sending and returns a
discriminated `ok` result. Claim errors/throws/malformed data yield `claim_failed`;
unexpected processing or unacknowledged completion yields `dispatch_failed`.
The worker returns safe HTTP 503 for either failure or initialization failure.
Missing `CRON_SECRET` is 503; incorrect Authorization remains 404. There is no GET.

A valid empty array is healthy HTTP 200. Provider rejection, unknown provider
outcome, and payload validation failure remain healthy processing outcomes when
their failed/unknown state is successfully persisted. A completion failure is
not treated as a provider failure or followed by a second completion attempt.
No raw database/provider errors, recipient data, or headers appear in responses
or new infrastructure logs. Failure counters/notification booleans are zero/false;
they do **not** prove that no earlier delivery in that batch reached the provider.

Business callers retain best-effort dispatch after commit. Order confirmation
booleans are false on infrastructure failure. Payment acknowledgement, delivered
status and replacement attachment remain committed. Payment **enqueue** failure
retains its existing webhook retry behavior; F9 changes only dispatch health.

## Scheduler and secret model

Migration: `supabase/migrations/20260923161749_schedule_order_email_outbox_retry.sql`,
filename generated by Supabase CLI. Apply manually after independent review.

One named job, `picchuspot-order-email-outbox`, runs `*/15 * * * *` and queues
POST `https://picchuspot.com/api/internal/order-email-outbox`, JSON body `{}`.
It loads `picchuspot_order_email_worker_secret` from `vault.decrypted_secrets`
at execution time and constructs Bearer auth. That value must equal Vercel
production `CRON_SECRET`. Secret rotation requires updating both stores.
Neither a secret value nor secret-creation SQL is committed or stored in cron.job.
Missing/empty Vault data fails before scheduling and before each HTTP request.

Supabase's documented registration schemas are `pg_catalog` for pg_cron and
`extensions` for pg_net; the latter creates `net`. The migration follows these
schemas, checks Vault and the exact pg_net POST signature, and rejects duplicate
or different same-name jobs (including inactive jobs, another database/user/host/
port). An exact match preserves the existing job ID. RLS filtering is disabled
locally during inspection so insufficient operator privileges fail closed.

pg_net temporarily stores the resolved Authorization header in its internal
request queue, as required to send HTTP. Upstream pg_net 0.20 grants PUBLIC table
access. This migration revokes ALL on that queue from PUBLIC, anon and
authenticated and checks effective browser-role privileges. A privileged operator
can still inspect it: never dump queue headers or decrypted Vault data. No
outbox RPC, outbox table, provider idempotency semantics or application mutex changes.

Each POST claims at most 10 rows, once. Backlogs need subsequent scheduled runs;
there is no loop until empty and no immediate scheduler retry. The pg_net timeout
is 65 seconds to allow the existing 60-second Vercel worker budget.

Read-only checks after the future rollout:

```sql
SELECT jobid, jobname, schedule, active, database, username, nodename, nodeport, command
FROM cron.job WHERE jobname = 'picchuspot-order-email-outbox';

SELECT runid, status, start_time, end_time
FROM cron.job_run_details
WHERE jobid IN (SELECT jobid FROM cron.job WHERE jobname = 'picchuspot-order-email-outbox')
ORDER BY start_time DESC LIMIT 5;

-- Replace 123 with the request_id from this job's correlated log entry.
-- Return only status/transport metadata, not response headers or content.
SELECT id, status_code, timed_out, error_msg IS NOT NULL AS transport_error, created
FROM net._http_response WHERE id = 123;

SELECT count(*) FILTER (WHERE attempt_count < 3 AND status IN ('pending','failed')) AS retryable_pending_failed,
  count(*) FILTER (WHERE attempt_count < 3 AND status IN ('unknown','sending')
    AND idempotency_expires_at > now()
    AND (status = 'unknown' OR lease_expires_at <= now())) AS retryable_unknown_stale_sending,
  count(*) FILTER (WHERE status <> 'sent' AND attempt_count >= 3) AS exhausted_unsent,
  count(*) FILTER (WHERE status = 'unknown' AND idempotency_expires_at <= now()) AS expired_unknown
FROM public.order_email_deliveries;
SELECT delivery_kind, count(*) FROM public.order_email_deliveries
WHERE status = 'sent' GROUP BY delivery_kind;
```

pg_net is asynchronous: a successful cron run proves that SQL queued a request,
not that the worker returned 200. Cron does not automatically fail on HTTP 503.
Response retention is normally six hours; inspect promptly. The request-ID log
provides correlation, not automated alerting. Validate its visibility at rollout.
If unavailable, stop rollout verification rather than guessing from the newest
HTTP response. No external monitor or alert service is introduced by F9.

Rollback, if separately authorized: deactivate only this named cron job; retain
the outbox, its persisted keys, and shared extensions. Never drop pg_cron to
disable this job: that would remove unrelated schedules.
